# Rust implementation

Derived from [architecture](../architecture.md) § Rust implementation. The TypeScript packages are the reference; this
blueprint fixes how each of their rules is written in Rust so the output is the same bytes. The engine's own rules stay
in the [ground plan blueprints](../../006-ground-plan/blueprints/README.md); nothing here changes them.

## Workspace

`rust/` is one Cargo workspace (resolver 3, edition 2024), toolchain pinned in `rust/rust-toolchain.toml` and
`mise.toml`. The workspace forbids `unsafe_code` and denies `clippy::all` and `clippy::pedantic` (`[workspace.lints]`).
It allows, workspace-wide, the lints the code mirrors the reference by: `many_single_char_names` and `similar_names`
(the formulas' names), `too_many_lines` (functions that match the TypeScript ones), `missing_panics_doc` and
`missing_errors_doc`, `module_name_repetitions`. Casts the fixed-point core makes on purpose are allowed at their site.

| Crate                 | Implements                                | Depends on                                                 |
| --------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| `citymap-ground-plan` | `packages/ground-plan`                    | `indexmap`, `serde`, `serde_json`, `ethnum`, `rustc-hash`  |
| `citymap-history`     | `packages/history`                        | `citymap-ground-plan`, `regress`, `serde_json`             |
| `citymap-measures`    | `packages/measures` (what the CLI writes) | `citymap-ground-plan`, `serde`, `serde_json`               |
| `citymap-themes`      | `packages/themes`                         | `citymap-ground-plan`                                      |
| `citymap-svg`         | `packages/svg`                            | `citymap-ground-plan`, `citymap-themes`                    |
| `citymap-cli`         | `apps/cli`, binary `citymap`              | all of the above; `mimalloc` behind its `mimalloc` feature |

Dependencies point the same way as the TypeScript workspaces. Each dependency is the latest stable release when it is
added, declared once in `[workspace.dependencies]`; `Cargo.lock` is committed and pins the build.

## Types

- Domain names keep their TypeScript names in Rust case: `Snapshot`, `FileEntry`, `TreeNode`, `LotSeed`, `Plat`,
  `TownPlat`, `CutRecord`, `GridRecord`, `RadialRecord`, `ShareRecord`, `OldTown`, `City`, `Town`, `Road`, `Block`,
  `Lot`, `District`, `TownStats`, `PlatEvent`, `Options`.
- String unions are enums with the TypeScript spelling as their serialised name: `RoadClass`, `LandUse`, `Form`
  (`FlatForm`, `DistrictForm` as predicates), `BlockKind`, `Jog`, `Order`, `Camera`, `ThemeName`.
- `Pt { x: i64, y: i64 }`; `Dir` is `[i64; 2]`, serialised as a two-element array.
- Optional fields (`row`, `river`, `green`, `high`, `width`, `form`) are `Option`s, left out of JSON when `None`.
- Strings held many times over a fold (paths, identities, lot keys, share members) are `Arc<str>`.
- What a fold shares between commits is behind an `Arc`: a snapshot's file list and folder map, a built tree and its
  shares (`Built`), a town plat's shares, and a city's towns (`City.towns` is `Vec<Arc<Town>>`).

## Numbers

| TypeScript                                                                      | Rust                                                                                              |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| a `number` holding an integer                                                   | `i64`; debug builds assert the safe range (\|v\| < 2^53) where the blueprint does                 |
| `bigint` (`centroid`, `offsetFor`, `starved`, radial, connectors, `outlineFor`) | `i128`; every such product is below 2^110                                                         |
| `bigint` in `inCircle` (super-triangle terms reach 2^146)                       | `ethnum::I256`                                                                                    |
| `floorDiv`, `roundDiv`, `mulDiv`                                                | `i64::div_euclid` on `i128` intermediates; exact, so equal to the TypeScript results              |
| `isqrt` (exact below 2^53, Newton above)                                        | exact integer square root of `u128`                                                               |
| `Number(big)` before `isqrt` (outline scale, radial ratio)                      | `big as f64` (round to nearest, ties to even, as `Number` does), then exact `isqrt` of that value |
| `Math.imul`, `>>>`, `^` on seeds                                                | `u32::wrapping_mul`, `>>`, `^` on `u32` bit patterns                                              |
| `Math.round(n / 2)` in `delaunay`                                               | `floor_div(n + 1, 2)`                                                                             |
| `Infinity` start values (`extent`, `best`)                                      | `i64::MAX` and `i64::MIN`                                                                         |

- A fixed-point primitive called outside its preconditions (a divisor of 0, the zero vector, a negative square root) is
  a programming error: it panics, naming its error code, as integer division by zero does. TypeScript throws the same
  code; neither is reachable from valid input. Plats read from a lockfile are validated so their pitches are positive
  (`plat/bad-shape`).
- Rendering is floating point in both implementations. Rust performs the same IEEE operations in the same order: `f64`
  arithmetic, `f64::cos`, `f64::sin` and `f64::powf` (the same libm as JavaScriptCore on Linux), `Math.min` and
  `Math.max` as `f64::min` and `f64::max` over the same operands.
- `toFixed(n)` is `to_fixed(v, n)`: the exact decimal value of the double rounded half toward +∞ in magnitude, with a
  `-` only for a negative value (so `-0` prints `0.0`). `String(n)` of an integer is its decimal; of a `f64` it is the
  shortest round-trip form (`1.5`, `0`, `3`).

## Strings and order

- `compareKeys` is byte order on UTF-8 (`str::cmp`), equal to code point order.
- Git output is decoded with `String::from_utf8_lossy` per NUL-separated token, which replaces invalid sequences as
  `TextDecoder` does.
- `fnv1a` hashes UTF-8 bytes; `.length` where it is a measure (SVG label widths) is the UTF-16 length
  (`encode_utf16().count()`); `toUpperCase` and `toLowerCase` are `to_uppercase` and `to_lowercase`.
- Land-use rules are written as code, not regular expressions: ASCII-case-insensitive suffix and infix tests for the
  `/i` patterns, case-sensitive for the others; `.` in `^test_.*\.py$` excludes the four ECMAScript line terminators.
- The manifest parsers keep their regular expressions and run them on `regress`, an ECMAScript regular expression
  engine, so `\s`, `.`, `^` and `$` mean what they mean in JavaScript. Globs compile to the same source text.
- JSON values from manifests are read with `serde_json` (`preserve_order`); a duplicate key keeps its last value, as
  `JSON.parse` does.

## Iteration order

JavaScript's orders are reproduced exactly:

| TypeScript                                          | Rust                                                                                            |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| a record (`Record<string, T>`) whose order is read  | `IndexMap`, `shift_remove` for `delete` (no record key that is read in order is an array index) |
| a record only looked up                             | `HashMap` or `IndexMap`                                                                         |
| `Map`, `Set` iterated                               | `IndexMap`, `IndexSet`                                                                          |
| `toSorted`, `sort` (stable)                         | `sort_by` (stable) with the same comparator                                                     |
| `find`, `some`, `reduce` choosing the first or last | the same scan direction and tie rule                                                            |

No record's insertion order shows in the plat or the city: a plat parsed from JSON inserts keys in text order (sorted),
as `JSON.parse` does, so a rule reads a record in `compare_keys` order (a grid's `slots` claims) or by index (vacant
lots in slot order), never in the order it was made. A town's `shares` and an old town's member map are only looked up.

## JSON

- Canonical JSON (`canonical_json`): object keys sorted by byte order at every level, no whitespace, a trailing newline,
  `None` fields left out, integers only (`i64`s, which the engine's limits keep within 2^53). Strings are escaped as
  `JSON.stringify` escapes them: `"` and `\\`, `\b \f \n \r \t`, other controls below U+0020 as `\u00xx` (lowercase
  hex), nothing else.
- The plat, the lockfile and the city are serialised by `serde_json` straight from their types: struct fields are
  declared in byte order of their JSON names, `Record`s are `BTreeMap`s, and insertion-ordered maps (`Slots`, `Shares`)
  serialise through `json::sorted`. A test reads every serialised object back and checks its keys are sorted.
- `parse_plat`, `parse_lock`, `parse_city` deserialise with `deny_unknown_fields` (valibot's `strictObject`) and map the
  failures to the TypeScript codes: `plat/bad-json`, `plat/too-new`, `plat/bad-version`, `plat/bad-shape`,
  `lock/bad-json`, `lock/bad-shape`, `city/bad-json`, `city/bad-shape` (a repeated town key at `/towns`).

## Errors

- `CitymapError { code: ErrorCode, message: String, detail: Vec<(&'static str, String)> }`, implementing `Display`
  (`"{code}: {message}"`, as the TypeScript `message`) and `std::error::Error`.
- `ErrorCode` is an enum with one variant per TypeScript code, displayed as the code (`fixed/bad-divisor`, …,
  `engine/invariant`). The CLI adds `engine/unexpected` for an I/O failure outside the engine.
- Fallible functions return `Result<T, CitymapError>`; nothing else crosses a crate boundary.

## Caches and the drawn city

Nothing here changes output: each cache holds the result of a pure function of what it is keyed by, and the drawing a
fold defers is pure. Folding with and without the caches gives the same bytes (tested on the fold fixture).

- The locality cache (`TownCache.entries`) as the [fold blueprint](../../006-ground-plan/blueprints/fold.md) defines it,
  compared field by field (digest, name, depth, district, land and its widths) rather than as one key text, with the
  same check that the folder's own record is present.
- A part's tree (`KeptTree`): kept while the part's files, its tree options and the shares it made last time are the
  same. Building again from the same files and the shares it made gives the same tree and the same shares (sharing
  places every member it already holds), and a part's folders and their first commits follow from its files. A part's
  files are the range of the sorted list under its root (`under`), less its old towns' files; the range is compared by
  pointer first, then entry by entry. The whole tree an old town's part is judged by is kept the same way.
- A neighbourhood's grid (`KeptGrid`): the cells and slots of a grid laid on some land, kept while the grid's direction,
  origin and pitches and the land are the same.
- Land use per path, for a million paths (`USE_MEMORY`); the derived workspace groups and members per file list (`Arc`
  identity in place of `WeakMap`); the separate members per file list, declared workspaces, submodules and separations
  (`KeptMembers`, as TypeScript's `membersOf`); the memoised warp per town and diameter.
- Drawing waits: `lay` makes every plan decision and updates the plat, and keeps each town as a `TownDraft`
  (`LastTown`). `current_city` draws the city of the last lay: loop connectors, the warp, tints and labels, old towns
  lit by the last snapshot's files, the highways (each town to the town its part joins, found by `lay` and kept as
  `Current.joins`), the extent check, and the city's record of its separations (`separable`, `declared`) from the last
  snapshot. `lay_city` is `lay` then `current_city`, as TypeScript's `layCity`. An archetype switch draws the town it
  freezes from its draft. The CLI draws once, after the fold.
- Every `lay` checks the drawn outlines of its towns and old towns against `COORD_LIMIT` (`check_outlines`); the
  highways are checked when the city is drawn.

## History

- The same git commands, flags, environment (`GIT_NO_LAZY_FETCH=1`, repository variables cleared,
  `GIT_ALLOW_PROTOCOL=none` for blob reads) and hooks path as `packages/history`.
- `read_history` runs `git log` on a reader thread that parses commits, applies them to the tree state and sends
  snapshots over a bounded channel (`SNAPSHOT_QUEUE` = 64); the fold lays them in order on the calling thread. A
  snapshot shares its file list and folder map (`Arc`) with the previous one while a commit only edits files.
- The fold schedule is `schedule.rs` (`Strides`, `FOLD_STRIDES`, `fold_schedule`, `is_laid`, `laid_count`), the same
  arithmetic and rejections as `schedule.ts`; `read_history` resolves the target and counts its commits
  (`count_commits`) before the log, sends `HistoryEvent::Schedule` first, and builds a snapshot only for a laid commit.
  `run_lay` takes the strides for its tests; `main` passes `FOLD_STRIDES`, and no flag changes them.
- The tree state is a `BTreeMap` by path, so the sorted file list is its iteration.
- Manifest blobs are read through one `git cat-file --batch` per reader, one blob at a time as each commit asks for them
  (the blobs `Workspaces::wanted` names before the commit applies), the partial clone's held blobs listed once, a
  process that ends mid-answer replaced for the next blob, as in TypeScript. Commits that change no root manifest read
  nothing. A blob that cannot be read sends `resolve` back through the manifest's older blobs, newest first, read
  through `read_more` (TypeScript reads them per chunk, `Workspaces.fallbacks`); the answer is the same.
- Submodules: `gitmodules.rs` (`parse_gitmodules`, `is_safe_module_path`, its patterns on `regress`) and `submodules.rs`
  (`SubmoduleReader`, `expand_all`, `expand`, `Pins`) mirror `gitmodules.ts` and `submodules.ts`: the same git calls
  (`rev-parse --git-common-dir` once, `--git-dir=<data> --work-tree=<data> ls-tree -r -z`, `cat-file blob` for a nested
  `.gitmodules`), the same git-data lookup and its containment check (paths resolved lexically, as `path.resolve` and
  `path.relative` do), the same depth limit, the same expansion indices, the same synthetic commit and the same events.
  The tree state's gitlinks live in `Pins.gitlinks`.
- The reader thread applies one commit at a time, so `Pins` has no `prepare` and no `ready`: at each expansion point
  `move_pins` reads every moved pin, one after another, each named by the `.gitmodules` in force there, the blob of the
  root file in the tree state (a gitlink at `.gitmodules` is no file there, so it names nothing). The text is read
  through the `BlobReader`, once and only when a pin moved. `SubmoduleReader` keeps its readings (by parent git data,
  path, name and pin) only until `move_pins` ends and calls `forget`, so what stays is each gitlink's last expansion
  (`Pins::held`). A reading is a pure function of path, pin and name, so the readings are TypeScript's whatever its
  chunks. TypeScript's invariant for a pin `move` was not prepared for (`engine/invariant`) has no Rust counterpart.

## Security and observability

- Repository content stays data: paths never reach a shell (`std::process::Command` with arguments), regular expressions
  are built only from the manifests' own patterns, escaped as in TypeScript, and SVG text is escaped by `escape_text`.
  The limits (`MAX_FILES`, `MAX_PATH_BYTES`, `COORD_LIMIT`) are checked at the same points.
- Every event the TypeScript engine emits is emitted with the same code and the same detail fields in the same order,
  and the CLI prints them as the same `code key=value …` lines.

## Command line

- `args.rs` parses the command line by hand, as `node:util` `parseArgs` does in strict mode: `--name=value` or
  `--name value` for string options, bare booleans (a value is an error), positionals anywhere, `--` ends options.
  Messages and the usage text are the TypeScript ones.
- `--separate=<list>` names the separations on (`workspaces,submodules,apps` by default, empty for none), as the
  TypeScript CLI does; an unknown name is `cli/usage` with the TypeScript message.
- `--toggles=<list>` names the archetype toggles on, as the TypeScript CLI does: `corridor,tiers` by default, empty for
  none, an unknown name `cli/usage` with the TypeScript message.
- `run.rs` takes an `Io` trait (read file, write file, log, clock) as `Io` is injected in TypeScript.
- Exit codes: 0 success, 2 usage (with the usage on standard error), 1 any other failure. The summary line is
  `fold/done repository=… commits=… laid=… lots=… overflow=… ms=…`.

## Parity

- `bun run parity` (`scripts/parity.ts`) builds the Rust CLI in release mode (with `--features=a,b` passed to cargo),
  then for each repository under `~/.cache/citymap/repos` (or `$CITYMAP_REPOS`) in `PARITY` (takken.io, redux,
  studio-worker, game-ci-cli, livediagram, react; next.js with `--long`) runs both CLIs with `--no-history` and with a
  full fold, each writing `--out`, `--svg` and `--lock` (the fold) into its own temporary folder, and compares the files
  with `cmp`: city, SVG, lockfile, and the log with the summary's `ms=` blanked (`withoutTimings`).
- The `resume` mode saves a lock part way and resumes from it, in both CLIs: each folds its clone to the commit
  `resumePoint` names (`--to=<commit> --lock`), then folds on to HEAD with `--lock`. `resumePoint(commits)` is halfway
  through the commits whose fold lays the same windows as the whole history (`foldSchedule` zones equal), so the lock is
  one the uninterrupted fold could have saved. The CLIs' resumed outputs are compared with each other, and each CLI's
  city, SVG and lock with its own `fold` outputs: `parity/resumed repo=… saved=… same` or
  `parity/resume-differs repo=… saved=… files=<side>:<file>,…` (exit 1).
- Every mode writes the city with its measures. The `coverage` mode lays the single state with coverage reports in all
  four formats written into each clone at their usual paths (`coverageReports`: a quarter of up to 400 sources each,
  LCOV and Istanbul by absolute CI paths, Cobertura by a source root, JaCoCo by package, and one path no repository
  holds), so the parsers and the path matching are compared byte for byte too.
- The `partial` mode folds a blob-less `--no-checkout` clone (`--filter=blob:none` over `file://`, its upload-pack
  allowing filters and any object by id, as a promisor remote serves them), so each CLI fetches the laid commit's
  `.mailmap` when it has one. The CLIs' outputs are compared with each other, and each CLI's authors (`authorsOf`:
  `available` and every file's and lot's `authors`) with its own `fold` outputs: `parity/partial repo=… same` or
  `parity/partial-differs repo=… files=<side>:authors,…` (exit 1). `cloneArgs` names each mode's clone, and
  `UPLOAD_PACK` the upload-pack the partial clone and its later fetch use.
- The `checkout` mode folds a clone made with a checkout, whose working tree `.mailmap` (and `mailmap.file`, pointed at
  the same text) maps up to `CHECKOUT_AUTHORS` 200 of its authors' emails to one (`checkoutMailmap`), so a CLI that read
  the working tree would count fewer authors. Each such clone logs `parity/checkout-mailmap clone=… lines=…`. The CLIs'
  outputs are compared with each other, and each CLI's city, SVG, lock and log with its own `fold` outputs (a
  `--no-checkout` clone): `parity/checkout repo=… same` or `parity/checkout-differs repo=… files=<side>:<file>,…` (exit
  1).
- `--toggles=<list>` passes the same flag to both CLIs, so one run proves one toggle setting: the defaults (no flag),
  each toggle alone (`--toggles=corridor` and so on) and none (`--toggles=`).
- `--separate=<list>` passes the same flag to both CLIs, as `--toggles=` does: the defaults (no flag), each separation
  alone and none (`--separate=`). The shared clones carry no `.git/modules` and no working tree, so a cached
  repository's submodules read there as unread (`.gitlink` files); initialised and nested submodules are proved by
  running both CLIs on copies of a repository that holds their git data.
- One line per run: `parity/same repo=… mode=… ts-ms=… rs-ms=…` or `parity/differs repo=… mode=… files=… …` (exit 1),
  the second followed by `parity/kept repo=… dir=…` where every mode's outputs for the repository stay; a missing
  repository is `parity/skipped reason=no-repository`. The run ends with a Markdown table of outputs and timings.
- A lockfile the TypeScript engine wrote checks a long fold without running TypeScript again: the Rust CLI folds a
  shared clone to the lock's commit with `--lock`, and its lockfile must be the same bytes.
- The CLIs read and write `citymap.lock.json` at the repository root, so each run gets its own
  `git clone --shared --no-checkout` of the clone (with a checkout in the `checkout` mode), under the repository's own
  name in a temporary folder: no lock is ever written into the shared clones, and neither CLI resumes from the other's
  lock.

## Testing

- Every TypeScript unit test of the engine, history, themes, svg and CLI is ported to a Rust test of the same behaviour,
  named after it, beside the code (`#[cfg(test)]`) or in `tests/`.
- Golden towns: the Rust test reads `packages/ground-plan/src/town/__golden__/*.json` and compares bytes; the TypeScript
  test writes them.
- Parity fixtures under `rust/fixtures/` are written by `scripts/parity-fixtures.ts` from the TypeScript engine:
  `land-use.tsv` (every path in `react-head-paths.txt` and a list of edge cases), `fold.json` (a synthetic history of
  groups, separate apps, edits, deletions, a rename and a root switch, its events per commit, its city and its plat,
  with every toggle off), `fold-defaults.json` and `fold-all.json` (that history grown by a corridor, an app of plugins
  and four packages, folded with the default toggles and with all four), `colours.tsv` (every colour of every theme for
  every district class and form), `svg.tsv` and `city.svg` (the folded city drawn in every theme, camera and region
  setting, as lengths and digests, one whole) and `usage.txt`.
- The toggles' forms are laid whole in `town/toggled.rs`, the TypeScript `town/toggles.test.ts` case by case.
- `cargo test` runs in under ten seconds on the development machine; the parity script is local, not in CI.

## Known differences

Only on input the TypeScript CLI would also reject, or never meets:

- A lockfile with a grid pitch of 0 is `plat/bad-shape` in Rust and `fixed/bad-divisor` at lay time in TypeScript.
- JSON numbers written with a fraction or an exponent (`1.0`, `1e3`) are rejected where valibot accepts an integer.
- `--density` accepts what `Number` accepts for integers, hexadecimal, octal and binary prefixes included; other
  `Number` forms (a lone sign, Unicode spaces) may differ, and both reject what is not an integer from 20 to 80.
- Usage and parse error messages from serde and the hand-written parser word their reasons differently; codes, exit
  codes and the usage text are the same.
- A city whose highways (not its outlines) cross `COORD_LIMIT` at a commit before the last fails in TypeScript and is
  only checked at the last commit in Rust.
- `parseSnapshot` (untrusted snapshot JSON) has no Rust counterpart: Rust snapshots come only from its own reader.

## Allocator

- `citymap-cli` has one cargo feature, `mimalloc` (off by default), which sets `mimalloc::MiMalloc` as the global
  allocator in `main.rs`. Without it no crate compiles C. The allocator changes speed only, never output: parity runs
  with and without it are byte-identical.
- `bun run rust:lint:mimalloc` runs clippy over the feature, in CI after `bun run rust:check`.
